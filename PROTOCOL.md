# Remote Terminal — Wire Protocol v3

All three components (relay, agents, Android app) speak this protocol.

**Protocol version: `3`.** Version 3 replaces the room-based v2 model with an
explicit identity model: an **account** owns many **agents** (machines) and
many **devices** (phone installs); each agent hosts many **sessions**
(terminals). v2 clients are not compatible with a v3 relay (see
[Compatibility](#compatibility-with-v2)).

- Transport: one **WebSocket** per client. Every application message is a UTF-8
  **JSON object** with a `type` field. Terminal payloads are carried as JSON
  strings (never base64) so the wire stays debuggable.
- Identity operations (enrolment, pairing) are plain **HTTPS request/response**
  on the same host, so the WebSocket has exactly one authentication path.
- Transport must be **`wss://`/`https://`** in production; `ws://`/`http://`
  is accepted for local development only.

---

## 1. Vocabulary & identifiers

| Term | Id prefix | Meaning |
|---|---|---|
| account | — | Owner of agents and devices. v3.0 relays have one account (`default`) per enrolment token. |
| agent | `a_` | One machine running the agent. Stable identity that survives restarts and renames. |
| device | `d_` | One phone install (the Android app). |
| session | `s_` | One terminal (PTY) on an agent. Called a *terminal* in the UI. |
| connection | `c_` | One live WebSocket. A phone connection is called a **client** when seen from the agent. |

Identifiers are the prefix plus **20 lowercase base32 characters**
(`[a-z2-7]`), e.g. `a_k3x7m2q9p4w8n6b5v1c0`. They are generated by the relay
from a CSPRNG and are **never secrets**: presenting an id grants nothing.

Secrets (`enrollToken`, `agentToken`, `deviceToken`) are opaque strings; the
relay stores only their SHA-256 hash and compares hashes in constant time.
Agent and device tokens are 32 random bytes encoded as base64url (43 chars).

Request correlation: any request may carry `reqId` (client-chosen, 1–40
chars of `[A-Za-z0-9_-]`); the matching reply or `error` echoes it.

In routed messages the routing keys are the short names `agent`, `session`,
`device`, `client`. Inside descriptive objects the keys are `agentId`,
`sessionId`, `deviceId`.

### Descriptive objects

```jsonc
// AgentInfo (relay → phone)
{ "agentId": "a_…", "name": "Production Server", "hostname": "prod-01",
  "platform": "linux",            // "win32" | "linux" | "darwin"
  "os": "Ubuntu 24.04", "arch": "x64", "agentVersion": "0.5.0", "protocol": 3,
  "shells": [ { "id": "bash", "label": "bash", "default": true }, { "id": "sh", "label": "sh" } ],
  "caps": ["sessions", "replay", "resize", "ping"],
  "online": true, "lastSeen": 1725264000000,   // ms since epoch
  "instanceId": "…",              // changes every time the agent process restarts
  "sessions": [ /* SessionInfo */ ] }

// SessionInfo
{ "sessionId": "s_…", "title": "API Logs", "shell": "bash",
  "state": "running",             // "running" | "exited"
  "createdAt": 1725264000000, "lastActiveAt": 1725264100000,
  "cols": 120, "rows": 35, "seq": 48211,   // output stream position (see §6)
  "attached": 1,                  // number of attached clients
  "exitCode": null }

// DeviceInfo
{ "deviceId": "d_…", "name": "Pixel 8", "createdAt": 1725264000000,
  "lastSeen": 1725264100000, "online": true, "isSelf": false }
```

## 2. HTTP endpoints (identity)

JSON bodies, at most 8 KiB. Responses carry `Cache-Control: no-store`. Error
responses are `{ "error": "<code>", "message": "…" }` with codes from §8.

| Method & path | Auth | Purpose |
|---|---|---|
| `POST /v3/enroll` | `Authorization: Bearer <enrollToken>` | Register a new agent. Body: `{name?, hostname, platform, os, arch, agentVersion, protocol}`. → `201 {agentId, agentToken, accountId, name}`. The token is returned **once**. |
| `POST /v3/pair/code` | Bearer **agent** or **device** token | Mint a pairing code for the caller's account. → `201 {code, expiresAt, ttlSec}`. One active code per caller; minting again replaces it. |
| `POST /v3/pair/redeem` | none | Body: `{code, deviceName, platform?, appVersion?}`. → `201 {deviceId, deviceToken, accountId}`. Single use. |
| `GET /v3/agents/me` | Bearer agent token | The caller's `AgentInfo` (without sessions). |
| `PATCH /v3/agents/me` | Bearer agent token | Body `{name}` → updated `AgentInfo`. |
| `GET /health` | none | `ok` |
| `GET /stats` | none | `{uptimeSec, connections, agentsOnline, phonesOnline, sessions, protocol}` — never ids or names. |

Pairing codes are **6 digits**, valid for `pairing.ttlSec` (default 300 s),
bound to one account, single-use, and locked after 5 wrong guesses. Redeem
attempts are limited per source IP (5/min, then a 15-minute lockout) and by a
global budget (relay-wide failed attempts per minute), so codes cannot be
brute-forced by spreading guesses across addresses. `X-Forwarded-For` is only
honoured when the relay is configured with `TRUST_PROXY=1`.

Enrolment is limited per IP (10/min). An account has caps on agents and
devices (`MAX_AGENTS_PER_ACCOUNT`, `MAX_DEVICES_PER_ACCOUNT`).

## 3. WebSocket connection

```
wss://<host>/?v=3&role=agent
wss://<host>/?v=3&role=phone
Authorization: Bearer <agentToken | deviceToken>
```

- `v=3` is required. A missing or different version is refused with close code
  **4426** (see [Compatibility](#compatibility-with-v2)).
- `role` is `agent` or `phone`.
- The bearer token may also be given as `token=` in the query string for clients
  that cannot set headers. This is discouraged (URLs end up in proxy logs).
- Optional `caps=` (comma-separated) advertises client capabilities (§9).

On success the relay sends `welcome` as the first message. On failure it sends
`error` and closes with a 44xx code.

```jsonc
// phone
{ "type": "welcome", "v": 3, "role": "phone", "connId": "c_…",
  "accountId": "default", "deviceId": "d_…",
  "caps": ["sessions", "replay", "ping", "pairing"],
  "limits": { "maxSessionsPerAgent": 16, "maxSessionsPerAccount": 64,
              "maxInputBytes": 1048576, "maxFrameBytes": 1048576 },
  "agents": [ /* AgentInfo… */ ], "devices": [ /* DeviceInfo… */ ] }

// agent
{ "type": "welcome", "v": 3, "role": "agent", "connId": "c_…",
  "accountId": "default", "agentId": "a_…", "name": "Production Server",
  "caps": [...], "limits": { "maxSessionsPerAgent": 16, "maxInputBytes": 1048576, "maxFrameBytes": 1048576 } }
```

Only one live connection per agent: a newer connection replaces the older one,
which is closed with **4409**. A device may hold several connections (e.g. a
phone and a tablet paired as separate devices, or one device reconnecting
before the old socket was reaped); each is an independent client.

Both sides may send `{ "type": "ping" }`; the peer answers `{ "type": "pong" }`.
The relay additionally uses WebSocket-level ping frames every `HEARTBEAT_MS`
and terminates sockets that miss a pong.

### agent → relay

```jsonc

  "sessions": [ /* SessionInfo… (sessions that survived the disconnect) */ ] }

{ "type": "agent.update", "name": "Office PC" }               // agent-side rename (CLI)

{ "type": "session.created", "reqId": "…", "client": "c_…", "session": { /* SessionInfo */ } }
{ "type": "session.attached", "reqId": "…", "client": "c_…", "session": "s_…",
  "from": 47000, "seq": 48211, "cols": 120, "rows": 35 }     // see §6
{ "type": "session.updated", "session": "s_…", "title": "…", "cols": 120, "rows": 35, "state": "running" }  // any subset
{ "type": "exit",           "session": "s_…", "code": 0 }     // shell process ended; session stays until closed/expired
{ "type": "session.closed", "session": "s_…", "reason": "closed" }  // "closed" | "exited" | "idle" | "shutdown" | "limit"
{ "type": "output",         "session": "s_…", "seq": 48211, "data": "…" }               // live: fan-out to attached clients
{ "type": "output",         "session": "s_…", "seq": 47512, "data": "…", "client": "c_…" } // replay: unicast to one client
{ "type": "error", "reqId": "…", "client": "c_…", "code": "limit_reached", "message": "…" } // reply to a client request
{ "type": "ping" }
```

### relay → agent

```jsonc
{ "type": "agent.registered", "agentId": "a_…", "name": "…" }
{ "type": "agent.updated",  "name": "…" }                       // renamed from a phone
{ "type": "session.create", "reqId": "…", "client": "c_…", "shell": "bash", "cols": 120, "rows": 35, "title": "…" }
{ "type": "session.attach", "reqId": "…", "client": "c_…", "session": "s_…", "since": 47000, "cols": 120, "rows": 35 }
{ "type": "session.detach", "client": "c_…", "session": "s_…" }
{ "type": "client.gone",    "client": "c_…" }                   // that phone connection closed: detach it everywhere
{ "type": "session.close",  "session": "s_…" }                  // kill the shell
{ "type": "session.rename", "session": "s_…", "title": "…" }
{ "type": "input",  "session": "s_…", "data": "ls\r" }
{ "type": "resize", "session": "s_…", "cols": 100, "rows": 40 }
{ "type": "pong" }
{ "type": "error", "code": "…", "message": "…" }
```

The relay strips `agent` from phone messages before forwarding (the agent
connection *is* the agent) and strips `client` from agent messages before
forwarding to a phone.

## 6. Output stream, sequence numbers & replay

Each session has one **output stream**. `seq` counts the UTF-16 code units of
everything the shell has ever emitted on that session; every `output` message
carries the position **after** its `data`, so a receiver holding `lastSeq`
knows the chunk is new iff `seq > lastSeq` and contiguous iff
`seq - data.length == lastSeq`.

The agent keeps the most recent `REPLAY_BYTES_PER_SESSION` units of each
stream in a ring buffer covering the range `[base, head)`; trimming happens on
line or escape-sequence boundaries so a replay never starts inside a sequence.
Live output is coalesced per session (about every 16 ms, chunks ≤ 32 KiB).

### Attach

```
phone   → session.attach { session, since?, cols, rows }
agent   → session.attached { from, seq: head, cols, rows }        (unicast)
agent   → output { seq, data, client }  ×N  covering [from, head)   (unicast)
agent   → output { seq, data }          …   live from then on       (fan-out)
```

- `from = since` when `since` is inside `[base, head]`; otherwise `from = base`
  (the phone missed more than the buffer holds) — the phone prints an
  *output lost* marker and soft-resets its screen (keeping local scrollback)
  before applying the replay.
- The phone should send `since` only when its terminal geometry is unchanged
  since it recorded `lastSeq`; otherwise it omits `since` and takes a full
  replay, because a delta was rendered for a different width.
- After replay the agent resizes the PTY to the attaching phone's `cols`/`rows`
  (last writer wins) and, if that changed anything, broadcasts
  `session.updated {cols, rows}` so other attached phones follow.
- Relay bookkeeping: a phone becomes *attached* only when the agent's
  `session.attached` acknowledgement passes through the relay. Live `output`
  is fanned out to attached phones only. The relay sends `client.gone` to the
  agent when a phone connection closes, and drops all attachments of an agent
  when the agent reconnects (phones re-attach on `agent.online`).
- Phones ignore live `output` for a session while an attach is pending, drop
  any chunk whose `seq` ≤ `lastSeq`, and re-attach with `since` when they
  detect a gap or receive `session.lag`.
- Terminal query replies (DSR, DA) must be **muted** while applying replayed
  output; they would otherwise inject stale answers into the shell.
- `instanceId` changes when the agent process restarts; all of its old sessions
  are gone, and phones must discard cached `lastSeq` values for that agent.

### 6a. Sending a file into a session

A phone can push a small file — a pasted image, in practice — to the machine
hosting a session it is **attached** to. The relay checks the same
authorization as `input` and forwards the frames without inspecting them.

```
phone   → file.begin { reqId, session, name, mime, size }
phone   → file.chunk { reqId, session, seq: 0, data }      base64, seq starts at 0 and increments
phone   → file.chunk { reqId, session, seq: 1, data }      …
phone   → file.end   { reqId, session }
agent   → file.stored { reqId, session, path, size }        or error { reqId, code }
```

- The agent writes chunks to a temporary file inside its upload directory
  (`UPLOADS_DIR`, default `<home>/RemoteTerminal`) and renames it into place
  only when the declared `size` has arrived, so a partial transfer never looks
  like a finished file.
- `name` is advisory: the agent keeps only the basename, replaces anything
  outside `[A-Za-z0-9._-]`, appends a timestamp, and never overwrites an
  existing file. Stored files are mode 0600, the directory 0700.
- Refusals come back as `error` with `limit_reached` (over `MAX_UPLOAD_BYTES`,
  default 16 MiB, or more than `MAX_UPLOADS` transfers in flight),
  `bad_request` (out-of-order chunk, more data than declared, incomplete at
  `file.end`) or `unknown_session`.
- Chunks must fit the frame limit; 192 KiB of raw data (256 KiB base64) is the
  size the app uses. A transfer that stalls for `UPLOAD_TIMEOUT_SEC` is
  discarded, as is everything in flight for a phone that disconnects.
- The capability is advertised by the agent as `files` in `AgentInfo.caps`;
  clients must not offer the feature to agents that lack it.

### Backpressure

The relay checks `bufferedAmount` of each phone socket before forwarding
output. Above the high-water mark it stops forwarding to that phone and, once
the socket drains again, sends `session.lag` for each session that lost
output. The phone then re-attaches with `since`. Agents pause their PTYs while
their own socket buffer is high.

## 7. Session lifecycle

```
session.create ──▶ running ──(shell exits)──▶ exited ──(retention)──▶ closed
                      │                          │
                      └──── session.close ───────┴──────────────────▶ closed
```

- **running**: the shell is alive. Attached or detached depends only on how
  many clients are attached; detaching never affects the process.
- **exited**: the process ended (`exit {code}`); the buffer is kept for
  `EXITED_RETENTION_SEC` (default 300) so the last output can be read.
- **closed**: removed from the agent (`session.closed {reason}`).
- A **detached** running session with no output for `SESSION_IDLE_TIMEOUT`
  (default 6 hours) is closed with `reason: "idle"`. Output resets the timer,
  so long-running jobs are not killed.
- Agent shutdown (SIGTERM) closes every session with `reason: "shutdown"`.
- A relay or phone disconnect never touches sessions.
- Limits: `MAX_SESSIONS_PER_AGENT` (agent-enforced and relay-enforced),
  `MAX_SESSIONS_PER_ACCOUNT` and `SESSION_CREATE_PER_MIN` per phone
  (relay-enforced). Exceeding one answers `error {code:"limit_reached"}`.

## 8. Errors & close codes

`error` messages carry a machine-readable `code`, a human `message`, and echo
`reqId`/`agent`/`session` when known. Nothing is dropped silently: a request
to an offline agent gets `agent_offline`, a message for an unknown session gets
`unknown_session`, an unauthorised id gets `forbidden`.

| code | meaning |
|---|---|
| `bad_request` | malformed JSON, unknown type, missing/invalid field, oversized field |
| `unauthorized` | missing or invalid token / pairing code |
| `forbidden` | the id exists but is not in your account, or you are not attached |
| `not_found` | unknown agent/device |
| `agent_offline` | request needs a live agent connection |
| `unknown_session` | the agent has no such session |
| `rate_limited` | per-connection or per-IP rate limit hit |
| `limit_reached` | a configured cap was reached (sessions, agents, devices, connections) |
| `unsupported_version` | protocol version mismatch |
| `internal` | relay-side failure |

WebSocket close codes used by the relay:

| code | meaning | client behaviour |
|---|---|---|
| `4401` | unauthorized / token revoked | phone: forget the device token and return to pairing; agent: stop reconnecting, mark identity invalid, require explicit `--enroll` |
| `4409` | replaced by a newer connection of the same agent | agent: stop reconnecting (another instance is running) |
| `4426` | protocol upgrade required (`v` missing or ≠ 3) | upgrade the client |
| `4429` | rate limit exceeded | reconnect with backoff |
| `4503` | connection/limit reached or relay shutting down | reconnect with backoff |

## 9. Capabilities

Advertised in `welcome.caps` (relay), `agent.register.caps` (agent, echoed in
`AgentInfo.caps`) and the `caps=` query parameter (phone).

| capability | meaning |
|---|---|
| `sessions` | multiple sessions per agent (required in v3) |
| `replay` | sequence-numbered replay on attach |
| `resize` | PTY resize is supported |
| `ping` | app-level ping/pong |
| `files` | the agent accepts files pushed into a session (§6a) |
| `pairing` | the relay exposes the `/v3/pair/*` endpoints |
| `color` | phone renders full SGR/ANSI (informational) |
| `legacy` | relay also serves v2 room clients (`LEGACY_V2=1`) |

Unknown capabilities and unknown message fields are ignored; unknown message
**types** are answered with `error {code:"bad_request"}` for phones and agents
alike.

## 10. Validation & limits (relay-enforced)

| item | rule |
|---|---|
| message | valid JSON object with a string `type`; ≤ `MAX_FRAME_BYTES` (default 1 MiB) |
| ids | `^[acds]_[a-z2-7]{20}$` |
| `reqId` | 1–40 chars `[A-Za-z0-9_-]` |
| `cols` / `rows` | integers, 1–500 / 1–300 |
| `data` (input) | string ≤ `MAX_INPUT_BYTES` (default 1 MiB) |
| `title`, `name` | 1–64 characters after trimming, no control characters |
| `shell` id | 1–32 chars `[A-Za-z0-9._-]`, must be one the agent advertised |
| message rate | phones `MSG_PER_SEC` (200), agents `AGENT_MSG_PER_SEC` (2000) |
| connections | `MAX_CONNS` global, `MAX_CONNS_PER_IP` |

The relay never inspects `data` beyond its type and size.

## 11. Security model (summary)

- Authentication is by bearer token only. Agent ids, device ids, hostnames,
  names and pairing codes carry no authority.
- The relay authorises every routed message: the target agent must belong to
  the caller's account; `input`/`resize` additionally require the caller to be
  attached to that session. Failures are answered with `forbidden` and logged.
- Revocation is pushed: `agent.remove` and `device.revoke` close live sockets
  with `4401`, delete the stored hash, and are broadcast to the account.
- Tokens and pairing codes are never logged; the relay logs `connId`,
  `agentId`, `sessionId`, `role`, `v` and sizes only. Terminal contents are
  never logged.
- The relay executes nothing; it forwards opaque terminal bytes.

## Compatibility with v2

v2 clients identify themselves by `room=` and no `v=` parameter. A v3 relay
refuses them with `error {code:"unsupported_version"}` and close code
**4426**, unless it is started with `LEGACY_V2=1`. In legacy mode the relay
serves v2 rooms in a completely separate table: legacy agents are never
visible to v3 phones and legacy phones can never reach v3 agents, so a
mis-configured old client cannot interact with the wrong machine. Legacy mode
exists to ease a staged upgrade and is documented as deprecated.

The v2 message set (`welcome`, `status`, `paired`, `input`, `output`, `replay`,
`resize`, `exit`, `ping`/`pong`, `error`) is unchanged inside legacy mode.
